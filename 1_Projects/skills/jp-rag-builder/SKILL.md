# 業務マニュアル即時RAG構築エージェント — 社内文書をAIが正確に答えるナレッジベースへ変換

このスキルは、ユーザーから提供された社内文書（テキスト、Markdown、PDF内容の貼り付け等）を読み込み、
RAGシステムに最適化された構造化Q&Aデータに変換・出力します。
「AIに社内データを読ませても的外れになる」問題の根本原因であるデータ品質を、エージェントが自動的に解決します。

## ワークフロー

### Step 1: ルールベースのロードと文書タイプ判定
`references/rag-guidelines.md` をロードし、6種類の文書タイプ別チャンキング戦略・メタデータスキーマ・Q&A品質ルールをコンテキストに取り込む。

ユーザーから提供された文書の内容を分析し、以下のいずれかの文書タイプに自動判定する：
- **(1) 業務マニュアル**: 手順書・作業指示書（Word/PDF由来）
- **(2) FAQ集**: 既存のQ&Aリスト（Excel/スプレッドシート由来）
- **(3) 社内規程・就業規則**: 条文形式の法的文書
- **(4) 議事録・ミーティングメモ**: 非構造化テキスト
- **(5) 暗黙知（ベテランノウハウ）**: ヒアリングメモ・口伝え
- **(6) チャットログ**: Slack/Teams/Chatworkの会話ログ

判定不能な場合はユーザーに確認する。

### Step 2: 前処理とチャンキング
文書タイプに応じた前処理を実施する。

**全文書タイプ共通の前処理:**
- 廃止・旧バージョンの情報がないか確認（更新日・バージョン情報を検出）
- フィラー・冗長表現の除去
- 固有名詞・社内用語の抽出

**チャンキング戦略（文書タイプ別）:**
- 業務マニュアル → 見出し単位（500〜800トークン、オーバーラップ10〜15%）
- FAQ集 → 1Q&Aペア = 1チャンク（分割しない）
- 社内規程 → 条文単位（但し書きは本条と一体化）
- 議事録 → 決定事項単位（雑談・感情表現は除外）
- 暗黙知 → 「状況→判断→理由」の1セット
- チャットログ → スレッド単位（非公式表現を公式化）

**重要ルール:** 表・リスト・箇条書きは1つの構造として保持し、絶対に途中で分割しない。

### Step 3: Q&A形式への変換とメタデータ付与
各チャンクを以下の構造のQ&Aペアに変換する：

**Q&Aペア1件に含める必須要素:**
- **質問文（メイン）**: ユーザーが実際に打ちそうな自然な言い回し
- **類似質問バリエーション（3件以上）**: 表記ゆれ・略語・否定形を網羅
- **回答文**: 結論先出し → 手順/条件 → 根拠/情報源 → 注意事項の構成
- **メタデータ**: id, department, category, effective_date, expiry_date, confidentiality, ai_answerable, source_documents, related_qa
- **免責文**: 「AIが生成した参考情報です。詳細は〇〇部に確認してください。」

**「AIが答えるべきではない」判定:** 個人の人事評価・法的判断・機密情報・健康相談・ハラスメント申告に該当する内容は `ai_answerable: false` を設定し、エスカレーション先を明記する。

### Step 4: 出力フォーマットの選択と生成
ユーザーの希望（または用途）に応じて、以下のいずれかの形式でQ&Aデータを出力する：

- **Markdown形式**（推奨・デフォルト）: YAML Front Matterでメタデータを保持。人間が読み書きしやすく、Agent Skillsのreferencesとしてそのまま利用可能。
- **JSON形式**: メタデータをフルに保持。LangChain/LlamaIndex/Dify等のRAGツールへの直接取り込みに最適。
- **CSV形式**: Excel管理との橋渡し用。UTF-8 BOM付き。

### Step 5: 品質チェックレポートの出力
変換結果の品質を自己チェックし、レポートを出力する：
- 変換したQ&Aペア数
- メタデータ完全性（必須フィールドの充足率）
- 有効期限切れ・古い情報のフラグ件数
- `ai_answerable: false`（エスカレーション必要）の件数
- 類似質問バリエーションの平均登録数
- 推奨改善アクション（不足情報の補完依頼等）

## Examples

**Example 1: 業務マニュアルの変換**
Input: 「経費精算について。経費精算は毎月末日締めとなります。翌月5日までに申請システムに入力し、領収書の原本を総務部に提出してください。承認は部長が行います。1万円以上の場合は役員承認も必要です。」
Output: Q「経費精算の締め日はいつですか？」/ 類似「経費の申請期限は？」「領収書はいつまでに出す？」「経費精算 締め」/ A「毎月末日が締め日です。翌月5日までに申請システムへの入力と領収書原本の総務部提出が必要です。承認フロー: 1万円未満→部長承認のみ、1万円以上→部長承認+役員承認。」/ メタデータ付き / Markdown形式で出力。

**Example 2: ベテランの暗黙知の形式知化**
Input: 「山田さん（勤続20年）が言ってたこと：取引先のA社は月初の3営業日は担当の佐藤さんが不在なので連絡が取れない。代理の人に言っても判断できないから、3日以降に改めて連絡する方がいい。」
Output: Q「取引先A社との連絡で注意すべきことは？」/ A「月初1〜3営業日は担当者（佐藤様）が定期外出で不在。代理担当者では即時判断が難しいため、急ぎでない案件は4営業日目以降に連絡を推奨。」/ メタデータに `source_person: 山田` `captured_date` を付与 / 半年ごとの要確認フラグ付き。

## Guidelines
- **最重要原則**: RAGの精度の8割は「データの純度」で決まります。技術より先にデータ整理が最優先です。旧バージョン・廃止情報が混入していないか必ず確認してください。
- 回答文は必ず「結論→詳細→根拠」の構造にすること。「担当者に聞いてください」だけの回答は禁止です。
- 表・リスト・箇条書きは絶対に途中で分割しないでください。意味が壊れます。
- 機密情報（人事評価・報酬・個人情報等）は `ai_answerable: false` を設定し、絶対にAIの回答に含めないでください。
