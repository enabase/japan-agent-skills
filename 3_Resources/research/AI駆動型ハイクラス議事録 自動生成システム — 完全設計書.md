# 🧠 AI駆動型ハイクラス議事録 自動生成システム — 完全設計書

> **対象読者:** AIエージェント開発者・プロジェクトマネージャー・業務効率化推進担当者  
> **目的:** VTT/テキスト形式の音声書き起こしから「意思決定の記録」として機能する構造化議事録を自動生成するためのフレームワーク・アルゴリズム・プロンプト制約条件を体系化する

---

## 📐 PART 1｜構造化フレームワーク：外資系コンサル標準の「完璧な議事録」設計

### 1-1. 設計思想：ピラミッド・ストラクチャー原則

外資系コンサルティングファームにおける議事録の根幹は、**結論→根拠→詳細** という逆ピラミッド構造にある。読み手（特に経営陣）は「冒頭3行で会議の全容を把握できる」状態を最優先とする。

```
┌─────────────────────────────────────────────────────────┐
│  LAYER 0（冒頭）: 会議メタデータ + Executive Summary       │ ← 経営陣はここだけ読む
├─────────────────────────────────────────────────────────┤
│  LAYER 1（本文上部）: Decisions / Open Issues / Actions   │ ← 管理職はここまで読む
├─────────────────────────────────────────────────────────┤
│  LAYER 2（本文中部）: 議題別 論点・議論サマリー            │ ← 担当者はここまで読む
├─────────────────────────────────────────────────────────┤
│  LAYER 3（末尾）: 発言ログ・補足・参照資料リンク            │ ← 検証時に参照
└─────────────────────────────────────────────────────────┘
```

[参照: 外資コンサル流「議事録作成術」の極意](https://note.com/taticodesportivo/n/n06c02b6a319a)

## 🔊 PART 2｜音声認識エラー・ノイズ補正アルゴリズム

### 2-1. ノイズの4分類と処理戦略

AIエージェントが内部処理で実施すべきフィルタリングを、ノイズの種類ごとに定義する。

```
┌────────────────────────────────────────────────────────────────┐
│              ノイズ分類マトリクス                                │
│                                                                  │
│  Type A: フィラー語 ──────────── → 完全除去                     │
│  Type B: 脱線・雑談 ──────────── → セクション隔離 or 除去        │
│  Type C: 発言のかぶり・重複 ───── → マージ/主発言者を優先        │
│  Type D: 専門用語の誤変換 ─────── → 辞書照合→推定補正→フラグ    │
└────────────────────────────────────────────────────────────────┘
```

---

### 2-2. Type A: フィラー語除去ルール

**除去対象リスト（完全一致・部分一致）:**

```python
FILLER_PATTERNS = [
    # 日本語フィラー
    r"えーっと", r"えー+", r"あの[ー〜]*", r"まぁ+", r"そうですね[ー〜]*",
    r"うーん+", r"なんか", r"ちょっと(?!した|した)", r"いや[ー〜]*(?!、)",
    r"あー+", r"んー+", r"そうそう", r"ですね[ー〜]*(?=\s)",
    # 冗長表現
    r"というか", r"みたいな感じで", r"〜的な", r"〜じゃないですか",
    r"っていうことで", r"という形で", r"させていただき"
]

# 処理方針: 除去後、前後の文脈を自然につなげる再整形処理を実施
```

**⚠️ 注意:** 「なんか」「ちょっと」は文脈によっては意味を持つ（例：「なんか問題があって」「ちょっと確認したい件がある」）ため、**文末・文中の位置と直後の品詞**によって判定する。

---

### 2-3. Type B: 脱線・雑談の検知と隔離ロジック

```
脱線検知アルゴリズム（疑似コード）:

function detectOffTopic(utterance, meetingAgenda):
  
  Step 1: トピックスコアリング
    - 現在の発言を埋め込みベクトル化
    - アジェンダ・直前5発言との コサイン類似度を計算
    - similarity < 0.35 → 脱線候補フラグ
  
  Step 2: 継続時間チェック  
    - 脱線候補が3発言以上連続 → 「雑談ブロック」として隔離
    - 1〜2発言のみ → 軽微なノイズとして除去
  
  Step 3: 議題復帰パターン検知
    - 「話を戻すと」「本題ですが」「さて、」等の
      トピック転換シグナルを検出し、直前ブロックを雑談と確定
  
  Step 4: 隔離 or 除去
    - 重要情報含む可能性あり → SECTION 8の末尾に「雑談ログ（参考）」
    - 完全に無関係 → 除去（補正ログに記録）
```

---

### 2-4. Type C: 発言かぶり・複数話者の重複処理

VTTファイルや音声書き起こしで頻発する**同時発言・割り込み**の処理方針：

| パターン | 処理方法 |
|---------|---------|
| 同意の相槌（「そうですね」「はい」「うんうん」）| 除去（主発言を保持） |
| 割り込み補完（前の発言の言い換え） | 主発言者の発言に統合してマージ |
| 反論・別意見の割り込み | 両者の発言を保持し「[{名前A} vs {名前B}]」タグで構造化 |
| 同時に異なる話題を話している | 話者分離スコアの高い方を「主発言」として採用 |

**話者識別の優先度:** タイムスタンプ付き話者ラベル > 声紋データ > 発言パターン推定

---

### 2-5. Type D: 専門用語・固有名詞の誤変換補正

```
補正パイプライン（3段階）:

Stage 1 — 辞書照合（確実補正）
  入力: 誤変換候補テキスト
  処理: プロジェクト専用辞書 + 業界用語辞書でルックアップ
  例: 「かーぴーあい」→「KPI」/ 「しーあーる」→「CR値 or CR施策」
  出力: 確定補正 → SECTION 7.2 の補正ログに記録

Stage 2 — 文脈推定（高信頼度補正）
  入力: Stage 1 で未解決のテキスト
  処理: 前後20トークンの文脈 + 会議アジェンダキーワードで
         確率的に最尤の用語を推定
  条件: 信頼度スコア > 0.80 のみ自動補正
  出力: 「推定補正（信頼度XX%）」としてフラグ付きで記録

Stage 3 — 要確認フラグ（低信頼度）
  入力: Stage 2 でも解決できない箇所
  処理: [要確認: {元テキスト}] タグを挿入し、
         ユーザーに確認を促すアラートをSECTION 7.3 に追加
  出力: 補正せず原文を保持（誤補正のリスクを回避）
```

## 🔍 PART 3｜文脈補完と欠落検知：曖昧TODOへのアラートシステム

### 3-1. 完全なアクションアイテムの定義（必須3要素）

```
完全なアクションアイテム = 担当者（WHO） × 内容（WHAT） × 期限（WHEN）

                    ┌──────────┐
                    │  WHAT    │  何をするか（動詞+目的語）
                    └────┬─────┘
              ┌───────────┴───────────┐
         ┌────┴───┐              ┌────┴────┐
         │  WHO   │              │  WHEN   │
         │担当者  │              │  期日   │
         └────────┘              └─────────┘

いずれか1つでも欠落 → 不完全アクション → アラート発火
```

---

### 3-2. 曖昧表現の検知パターン辞書

AIが「決まった風だが曖昧」なTODOを検知するためのトリガーパターン：

**【期日が曖昧なパターン】**

```python
AMBIGUOUS_DATE_PATTERNS = [
    "なるべく早めに", "できるだけ早く", "早急に", "速やかに",
    "近いうちに", "そのうち", "折を見て", "検討します",
    "確認しておきます", "追って連絡します", "来週中に",  # ← 「来週中」は相対表現でNG
    "月内に", "今月中に",  # ← 発話日が特定できない場合はNG
    "次回までに",  # ← 次回日程が未定の場合はNG
]
# → アラートレベル: WARNING ⚠️ 期日を「YYYY年MM月DD日」形式で特定してください
```

**【担当者が曖昧なパターン】**

```python
AMBIGUOUS_OWNER_PATTERNS = [
    "誰かが", "みんなで", "チームで", "各自", "それぞれ",
    "〜側で", "〜チームで",  # ← チーム名のみで個人特定なし
    "お願いします",  # ← 主語なしの依頼
    "〜してもらえますか",  # ← 受動的で責任者不明確
    "確認しましょう",  # ← 主語が「we」で責任者不明
]
# → アラートレベル: ERROR 🚨 担当者を個人名で特定してください
```

**【内容が曖昧なパターン】**

```python
AMBIGUOUS_CONTENT_PATTERNS = [
    "検討する", "考えてみる", "見ておく", "確認する",  # ← 何を検討/確認するか不明
    "うまくやっておいて", "いい感じに", "よろしくお願いします",
    "あとは任せます",  # ← 対象範囲・成果物不明
]
# → アラートレベル: WARNING ⚠️ アクションの具体的な成果物を定義してください
```

### 3-3. 3段階アラートレベル定義

```
┌─────────────────────────────────────────────────────────────────┐
│  🚨 ERROR（赤）: 議事録を送信する前に必ず修正が必要              │
│     条件: 担当者が完全に特定できない                             │
│     例:「誰かがやっておいてください」                            │
│     表示: [ERROR] タスク"X"の担当者が未特定です。              │
│            発言: "誰かがXXXを確認しておいてください"             │
│            → 担当者を個人名で特定してください。                  │
├─────────────────────────────────────────────────────────────────┤
│  ⚠️ WARNING（黄）: 推奨対応だが送信は可能                       │
│     条件: 期日が相対表現/不明瞭、内容が抽象的                   │
│     例:「なるべく早めに確認します」                              │
│     表示: [WARNING] タスク"Y"の期日が不明確です。              │
│            発言: "なるべく早めに確認します"                      │
│            → 「YYYY年MM月DD日」形式で期日を設定してください。    │
├─────────────────────────────────────────────────────────────────┤
│  ℹ️ INFO（青）: 参考情報。確認推奨だが問題なし                  │
│     条件: 発言から推定で補完できたが確認が望ましい               │
│     例: 「前回と同様に田中さんが担当」                           │
│     表示: [INFO] タスク"Z"の担当者を文脈から"田中氏"と推定しました。│
│            → 内容を確認の上、確定してください。                  │
└─────────────────────────────────────────────────────────────────┘
```

### 3-4. 文脈補完アルゴリズム（推定ロジック）

```
文脈補完フロー:

Input: 「来週の月曜日にXXXを確認しておきます」（発話者: 田中）

Step 1: 担当者推定
  → 発話者（田中）を担当者として自動抽出（確度: HIGH）
  → INFO アラート発火（推定補完済み）

Step 2: 期日推定
  → 「来週の月曜日」= 発話日の翌週月曜日
  → タイムスタンプから発話日を特定し、絶対日付に変換
  → タイムスタンプなし → WARNING アラート発火（「来週の月曜日」の絶対日付不明）

Step 3: 内容の具体化
  → 「XXXを確認」の「XXX」が直前の文脈から特定可能か検証
  → 特定可能 → 自動補完してINFOアラート
  → 特定不可 → WARNING アラート「確認対象が不明確です」

Step 4: 完全度スコア算出
  WHO: 1点 / WHAT: 1点 / WHEN: 1点 → 合計3点が「完全なTODO」
  2点以下 → SECTION 7.1 の不完全アクションリストに追加
```

## 📊 PART 4｜会議タイプ別 出力フォーマット切り替えマトリクス

### 4-1. 会議タイプ判定フロー

```
会議タイプ自動判定アルゴリズム:

Step 1: メタデータ確認
  - 会議名称に「定例」「進捗」→ TYPE_A（定例進捗会議）
  - 会議名称に「ブレスト」「アイデア」「企画」→ TYPE_B
  - 会議名称に「障害」「トラブル」「緊急」→ TYPE_C
  - 会議名称に「商談」「提案」「営業」→ TYPE_D

Step 2: 発言内容分析（メタデータ不明時）
  - 「進捗」「ブロッカー」「遅延」発言が多い → TYPE_A
  - 「アイデア」「どう思う」「〜はどうか」発言が多い → TYPE_B
  - 「エラー」「障害」「原因」「対応」発言が多い → TYPE_C
  - 「予算」「契約」「導入」「提案」発言が多い → TYPE_D

Step 3: 担当者によるマニュアル指定（最優先）
```

### 4-3. 会議タイプ別 セクション差分定義

#### TYPE A：定例進捗会議（Weekly / Sprint Review）

## 🤖 PART 5｜AIエージェントへの制約条件（プロンプトに組み込むべき指示書）

### 5-1. System Prompt テンプレート（Master Instruction）

```
# ROLE（役割定義）
あなたは、外資系コンサルティングファーム出身のシニアプロジェクトマネージャーが
作成するクオリティの「構造化議事録エージェント」です。
あなたの出力は「単なる会議の要約」ではなく、
「プロジェクトの意思決定記録」として機能しなければなりません。

# CORE CONSTRAINTS（絶対に守るべき制約）

[C-01] 決定事項と「議論された事項」を必ず分離せよ
  - 「〜という話が出ました」→ 議論事項（決定ではない）
  - 「〜に決まりました / 〜で進めます / 〜でいきましょう」→ 決定事項
  - 判断が難しい場合は OPEN ISSUES に分類し、フラグを立てよ

[C-02] アクションアイテムには必ず WHO/WHAT/WHEN を三位一体で記述せよ
  - いずれか1つでも欠落している場合は、SECTION 7.1 に不完全アラートを出力せよ
  - 「早めに」「近いうちに」「検討します」はWHEN=未設定として扱え
  - 「みんなで」「チームで」はWHO=未設定として扱え

[C-03] 元の発言を「解釈」するな。「構造化」せよ
  - 発言の意図を拡大解釈・憶測で補ったり、都合よく書き換えてはいけない
  - 不明確な点は [要確認] タグで明示し、判断をユーザーに委ねよ
  - 自分の意見や評価を議事録に混入させるな

[C-04] 経営陣が1分以内に状況把握できるようにせよ
  - SECTION 1（Executive Summary）は必ず3文以内に収めよ
  - 最重要の決定・リスク・アクションを優先して冒頭に配置せよ
  - 文体は書き言葉（文語体）、文末は「〜した」「〜である」で統一せよ

[C-05] ノイズを可視化し、補正を透明にせよ
  - 音声認識エラーを補正した場合は必ずSECTION 7.2に補正ログを残せ
  - フィラー・雑談を除去した場合も、除去件数をログに記録せよ
  - 話者特定に自信がない箇所は [発言者不明] タグを付与せよ

[C-06] 会議タイプを自動判定し、出力フォーマットを切り替えよ
  - 判定根拠を SECTION 7 の末尾に1行で明示せよ
  - 判定に迷う場合はユーザーに確認を促し、デフォルトはTYPE_A（定例進捗会議）とせよ

[C-07] 出力言語は議事録の本文言語（日本語 or 英語）に統一せよ
  - ただしプロジェクト名・ツール名・固有名詞は元の表記を保持せよ

# PROCESSING PIPELINE（処理順序）
1. 入力テキストの前処理（フィラー除去 → 話者分離 → 時系列整理）
2. 会議タイプ判定
3. 意思決定の抽出（決定/未決/議論の三分類）
4. アクションアイテムの抽出と完全度チェック
5. 議題別論点サマリーの生成
6. Executive Summary の生成（最後に、全体を見てから作成する）
7. 品質チェックレポートの生成（SECTION 7）
8. 最終出力の構造検証（全必須セクションの存在確認）

# OUTPUT FORMAT（出力形式）
- Markdown形式で出力すること
- テーブルにはMarkdown記法を使用すること
- セクション番号は必ず付与すること
- 文字数目安: Executive Summary 100文字以内 / 各議題サマリー200〜400文字

# HALLUCINATION PREVENTION（幻覚防止）
- 発言録に存在しない情報を「補完」してはいけない
- 数字・固有名詞・日付は必ず元テキストから根拠を取ること
- 根拠が取れない場合は [出典不明] タグを使用すること
- 「おそらく」「と思われる」等の推測表現は禁止。確証がない場合は記載しないか要確認タグを使用せよ
```

### 5-3. 品質評価スコアカード（AI自己評価用）

AIが最終出力前に自己チェックするための評価基準：

| チェック項目 | 基準 | スコア |
|------------|------|--------|
| Executive Summary が3文以内か | Y/N | /10pt |
| 全決定事項に「根拠・背景」が記載されているか | Y/N | /10pt |
| 全アクションアイテムにWHO/WHAT/WHENが揃っているか | Y/N | /20pt |
| 不完全TODOへのアラートが漏れなく出ているか | Y/N | /20pt |
| 補正ログが全補正箇所に対応しているか | Y/N | /10pt |
| 会議タイプに応じたセクション追加がされているか | Y/N | /10pt |
| 元発言に存在しない情報が混入していないか | Y/N | /20pt |
| **合計** | — | **/100pt** |

> 80点以上：出力可 / 60〜79点：WARNING付きで出力 / 59点以下：ユーザーに確認要求

## 📌 まとめ：「単なる要約」から「意思決定記録」への転換

```
❌ ダメな議事録（単なる要約）の特徴:
   ・時系列で「〜という話がありました」が並ぶ
   ・決定と議論が混在している
   ・TODOに担当者か期日のいずれかが欠けている
   ・参加者以外が読んでも何も分からない
   ・音声認識のノイズがそのまま残っている

✅ ハイクラス議事録（意思決定記録）の特徴:
   ・経営陣が1分で状況把握できる逆ピラミッド構造
   ・Decisions / Open Issues / Actions が明確に三分類
   ・全TODOにWHO×WHAT×WHENが揃い、不足はアラートで通知
   ・AIが自動補正した箇所が透明に可視化されている
   ・会議タイプに応じて最適なフォーマットに自動切り替え
```
