## 第1章：RAGが「的外れ回答」を返す原因の完全分類

> **この章で学べること：** なぜAIが「的外れ」な回答をするのか。技術的な問題ではなく「データと設計の問題」であることを理解し、対策の方向性を把握する。

### 1.1 チャンキング（文書分割）の粒度問題

「チャンキング」とは、長い文書をAIが検索しやすいように小さな塊（チャンク）に分割する工程です。この分割の粒度が不適切だと、回答精度が大きく低下します。

#### ■ チャンキング手法による精度比較

| チャンキング手法 | Faithfulness（回答忠実度）スコア |
|---|---|
| Naive（固定サイズ512トークン） | 0.47 〜 0.51 |
| Optimized Semantic（意味単位分割） | 0.79 〜 0.82 |

*出典：2025年 CDCポリシーRAG研究*

---

#### 1.1.1 チャンクが大きすぎる場合の失敗パターン

- LLMのコンテキスト上限を超えて情報が切り捨てられる
- 検索ヒット率は高いが、関係のない情報が混入して「ぼんやりした回答」になる
- **具体例：** 業務マニュアル全体1万文字を1チャンクにした場合、「経費精算の締め日は？」という質問に、交通費・交際費・福利厚生など全セクションが検索され、AIが混乱する

#### 1.1.2 チャンクが小さすぎる場合の失敗パターン

- 文脈が失われ、単語レベルの断片が検索にヒットする
- **具体例：** 「承認が必要」というチャンクだけが返ってきて、「何の承認？」「誰が承認？」の文脈が消える
- 回答精度がNaive固定サイズで Faithfulnessスコア 0.47〜0.51 に低下

#### 1.1.3 表・リスト・箇条書きが分割されて意味を失うケース

- 固定サイズ分割で、表の「見出し行」と「データ行」が別チャンクに分かれる
- 箇条書き3項目のうち2項目が別チャンクに入る
- 「なし」「対象外」「→次項参照」などの不完全な断片が単独でヒットする

#### 1.1.4 章・節・見出しの階層構造がチャンキングで壊れるケース

- 「第3条（個人情報の取り扱い）」と「前条の目的達成に必要な範囲で...」が別チャンクになり、「前条」の参照先が失われる
- 見出しのコンテキストが消えて「この手順は何の手順か」が不明になる

```
【具体的な失敗例】

チャンク A: 「...規制基準に従い...」
チャンク B: 「取締役会は3つの新しい...」

→ LLMはAとBの文脈なしに関係性を合成しようとし、
   ソースに存在しない因果関係をハルシネーションする。
```

---

### 1.2 メタデータ不足による検索精度低下

「メタデータ」とは文書に付ける「付箋情報」のことです。「いつの情報か」「どの部署のルールか」が管理されていないと、AIは古い情報や間違った部署のルールを回答してしまいます。

#### 1.2.1 「いつ時点の情報か」が不明な場合

- 2020年の就業規則と2024年改定版が混在し、AIが古い規則を自信満々に回答
- **実際の事故例：** 廃止された残業申請フローをAIが案内し、申請漏れによる給与未払いが発生

#### 1.2.2 「どの部署のルールか」が不明な場合

- 営業部の「訪問前承認不要」ルールと総務部の「全訪問要事前申請」ルールが混在
- 部署メタデータがないため、全社員に矛盾した回答が返る

#### 1.2.3 同じ用語が部署ごとに異なる意味で使われている場合

| 用語 | 営業部での意味 | 品質管理部での意味 |
|------|---|---|
| クレーム | 顧客からの苦情 | 製品の不具合申告書 |
| 承認フロー | 1段階承認 | 3段階承認 |
| 単価 | 販売価格 | 製造原価 |

### 1.3 元文書の品質問題

#### 1.3.1 暗黙知（書かれていない前提知識）の欠落

- 「Aシステムに登録する」と書いてあるが、Aシステムへのログイン方法・権限申請方法が書かれていない
- 「担当者に確認する」と書いてあるが、担当者が誰かが書かれていない
- 長年の慣例（例：「月末最終金曜は全社集荷日のため発送不可」）が文書化されていない

#### 1.3.2 更新されていない古い情報と最新情報の混在

- 「●●部長の承認を得る」と書いてあるが、その人は3年前に退職
- システムのUIが変わり、スクリーンショット付き手順書が現実と乖離
- 同じドキュメントが3つのストアに4つのバージョンで存在し、検索がランダムに古いバージョンを返す

```
【最悪のパターン】
4バージョン × 3ストア = 12の重複ドキュメント
チャンクレベルでは数百の重複
検索はランダムに古いバージョンを返す
ユーザーは矛盾した回答を受け取る
```

#### 1.3.3 手順書に「なぜそうするのか」の理由が書かれていない

- 「必ずBCC:にXXXを入れること」とだけ書いてあり、理由が書かれていないため、状況が変わっても誰も削除できない
- 例外状況でどう判断すればいいかわからない

### 1.4 RAGが本番で死ぬ7つの死因

*出典：Qiita「RAGが本番で死ぬ本当の理由」3,540時間のAI対話実験より*

| # | 死因 | 発生確率 | 根本原因 |
|---|------|---------|---------|
| 1 | チャンク境界の意味破壊 | ★★★★★（失敗の80%） | 固定サイズで意味の境界を無視して切断 |
| 2 | 埋め込みの経年劣化 | ★★★★☆（6ヶ月後に顕在化） | ドメイン言語の変化でベクトルが陳腐化 |
| 3 | ハルシネーションの変態 | ★★★★☆ | RAG後は「もっともらしい誤り」になり発見困難 |
| 4 | セキュリティの崩壊 | ★★★☆☆ | ACL権限設定なしで全データが全員に見える |
| 5 | スケール時の精度崩壊 | ★★★☆☆ | 1万件→1億件でRecallが0.95→0.71に低下 |
| 6 | コスト爆発 | ★★☆☆☆ | 不要なクエリにもRAGフル稼働（月額45万円の無駄） |
| 7 | ドキュメント品質の腐敗 | ★★★★★（根本原因） | 重複・矛盾・旧バージョンが共存 |

> ⚠️ **重要：** 精度の8割はアルゴリズムの性能ではなく、「学習データの純度」で決まります。技術的な最適化より先に、データ整理が必須です。

## 第2章：社内文書タイプ別の最適な構造化・変換手法

> **この章で学べること：** 6種類の社内文書タイプそれぞれに最適な変換方法を知り、具体的なBefore→Afterの実例でイメージを掴む。

---

### 2.1 業務マニュアル（Word/PDF）— 手順書・作業指示書

#### 前処理フロー

1. OCR処理（スキャンPDFの場合）
2. 見出し階層の抽出（H1/H2/H3を特定）
3. 手順番号・箇条書きの構造化
4. スクリーンショット画像の代替テキスト付与
5. 廃止・旧バージョンドキュメントの除外

#### チャンキング戦略

- 見出し単位でチャンキング（1手順 = 1チャンク）
- チャンクサイズ目安：**500〜800トークン**（日本語約400〜600文字）
- オーバーラップ：**10〜15%**（前の手順との接続部分を含める）
- 表・リストは1つの構造として保持（**分割しない**）

#### メタデータ付与ルール

```json
{
  "doc_type": "manual",
  "department": "総務部",
  "category": "経費精算",
  "version": "v3.2",
  "effective_date": "2024-04-01",
  "expiry_date": "2025-03-31",
  "author": "総務部 田中",
  "last_reviewed": "2024-12-01",
  "confidentiality": "internal",
  "source_file": "経費精算マニュアルv3.2.pdf"
}
```

#### Before → After 実例

**Before（生の文書テキスト）**

```
経費精算について
経費精算は毎月末日締めとなります。翌月5日までに申請システムに入力し、
領収書の原本を総務部に提出してください。承認は部長が行います。
1万円以上の場合は役員承認も必要です。
```

**After（RAG用 Q&A形式 Markdown）**

```markdown
## Q: 経費精算の締め日はいつですか？

**A:** 毎月末日が締め日です。翌月5日までに申請システムへの入力と、
領収書原本の総務部提出が必要です。

**承認フロー:**
- 1万円未満: 部長承認のみ
- 1万円以上: 部長承認 + 役員承認（2段階）

**注意事項:** 領収書原本の提出がない場合、精算が保留されます。

_情報源: 経費精算マニュアルv3.2 | 更新日: 2024-04-01 | 担当: 総務部_
_関連: Q-045「立替払いの上限金額」、Q-067「交際費の扱い」参照_
```

### 2.2 FAQ集（Excel/スプレッドシート）— 既存のQ&Aリスト

#### 前処理フロー

1. ExcelからCSV/JSON変換
2. 重複Q&Aの統合・排除
3. 質問文の揺れ統一（「〜できますか？」「〜は？」形式を揃える）
4. 回答が「担当者に聞いてください」のみのものを特定・補完

#### チャンキング戦略

- **1Q&Aペア = 1チャンク**（分割しない）
- 複数の質問文バリエーションを同一チャンクに含める（類似質問マッピング）

#### Before → After 実例

**Before（Excelの表形式）**

| 質問 | 回答 |
|------|------|
| 有給はどうすれば取れますか | システムで申請してください |

**After（RAG用 JSON）**

```json
{
  "id": "FAQ-HR-042",
  "questions": [
    "有給はどうすれば取れますか",
    "有給休暇の申請方法を教えてください",
    "休暇の取り方",
    "年休の申請手順"
  ],
  "answer": "有給休暇は以下の手順で申請できます：\n1. 勤怠管理システム（kintone）にログイン\n2. 「休暇申請」メニューを選択\n3. 取得日・休暇種別を入力し「申請」ボタンをクリック\n4. 直属上長の承認後に確定\n\n申請は取得希望日の3営業日前までに完了させてください。",
  "metadata": {
    "category": "人事・労務",
    "department": "全社",
    "effective_date": "2024-04-01",
    "confidence": "high",
    "source": "就業規則第15条",
    "related_qa": ["FAQ-HR-043", "FAQ-HR-051"]
  }
}
```

### 2.3 社内規程・就業規則（PDF）— 法的文書・条文形式

#### 前処理フロー

1. 条文番号・見出しの構造化
2. 「前条」「次条」「第XX条」などの内部参照を展開
3. 法律改正との差分チェック（改正年月日の明記）
4. 「この規程の解釈は〜部が行う」などの管轄情報の抽出

#### チャンキング戦略

- 条文単位でチャンキング（第1条〜第3条でグルーピングも可）
- **但し書き・除外事項は必ず本条と同一チャンクに含める**
- 罰則・制裁に関する条文は単独チャンクとして高優先度付与

#### Before → After 実例

**Before（条文テキスト）**

```
第15条（年次有給休暇）
本人の申請に基づき、前年度に全労働日の80%以上出勤した従業員に対し、
継続勤務年数に応じて年次有給休暇を付与する。ただし、勤務開始から6ヶ月間は
月末締めの翌月に審査する。
```

**After（RAG用 Q&A形式 Markdown）**

```markdown
## Q: 有給休暇は入社してすぐ取得できますか？

**A:** 入社後すぐには取得できません。

**付与条件:**
- 前年度の出勤率が80%以上であること
- 継続勤務年数に応じて付与日数が変わります

**入社初年度の特例:**
- 勤務開始から6ヶ月間は「月末締め翌月審査」の対象
- 入社から6ヶ月後の最初の月末に審査が行われ、付与日数が決定

**根拠:** 就業規則 第15条（年次有給休暇）
_改正日: 2024-04-01 | 次回見直し予定: 2025-03-31_
_⚠️ この解釈に疑問がある場合は人事部（内線: 123）に確認してください_
```

### 2.4 議事録・ミーティングメモ — 非構造化テキスト

#### 前処理フロー

1. 日時・参加者・議題の構造化抽出
2. 「決定事項」「アクションアイテム」「未決事項」の分類
3. 固有名詞（プロジェクト名・担当者名）の正規化
4. 発言メモの「非公式語」を公式語に変換
5. 個人の批判・感情的表現のマスキング

#### チャンキング戦略

- 「決定事項」単位でチャンキング
- 「〜について検討した」レベルの雑談は除外
- アクションアイテムは担当者・期限と1チャンクにセット

#### Before → After 実例

**Before（議事録テキスト）**

```
2024/11/15 経費精算システム刷新プロジェクト 第3回会議
田中部長から、新システムへの移行は来年4月を目標にする、との発言あり。
鈴木さんが現行システムの使いにくさを指摘。結局、移行スケジュールは
総務と情シスで別途調整することになった。
```

**After（RAG用 構造化 Markdown）**

```markdown
## 決定事項: 経費精算システムの移行時期

**内容:** 新経費精算システムへの移行目標を2025年4月に設定することが決定された。

**背景:** 現行システムの操作性に課題があり、刷新が必要との判断。

**アクションアイテム:**
- 詳細移行スケジュールの策定: 総務部・情報システム部 共同（期限: 2024年12月末）

**情報源:** 経費精算システム刷新PJ 第3回会議（2024-11-15）
**決定者:** 総務部 田中部長
**ステータス:** 対応中
```

### 2.5 属人化されたベテランの暗黙知 — ヒアリングメモ・口伝え

#### 前処理フロー（暗黙知の形式知化プロセス）

1. **構造化インタビューの実施**（以下の質問テンプレートを使用）
   - 「この作業で一番ミスが起きやすい場所は？」
   - 「新人に必ず教えることは何ですか？」
   - 「マニュアルに書いていないけど知っておくべきことは？」
2. 「**状況 → 判断 → 理由**」の三要素セットで記録
3. 複数のベテランへの同じ質問で矛盾がないか確認
4. 「〇〇さんだから知っているノウハウ」を「〇〇状況での対処法」に一般化

#### Before → After 実例

**Before（ヒアリングメモ）**

```
山田さん（勤続20年）が言ってたこと：
取引先のA社は月初の3営業日は担当の佐藤さんが不在なので連絡が取れない。
でも代理の人に言っても判断できないから、3日以降に改めて連絡する方がいい。
```

**After（形式知化後 Markdown）**

```markdown
## Q: 取引先A社との連絡で注意すべきことはありますか？

**A:** 月初の1〜3営業日は連絡のタイミングに注意が必要です。

**理由:** 担当者（佐藤様）が月初3営業日は定期外出のため不在。
代理担当者では即時判断が難しい案件も多いため、返答が遅れる傾向があります。

**推奨アクション:**
- 急ぎでない案件: 月初4営業日目以降に連絡する
- 急ぎの場合: 事前（月末まで）にA社に連絡を入れておく

_情報源: 山田（2024年12月 ヒアリング）| ナレッジ化日: 2024-12-10_
_⚠️ 担当者変更の可能性あり。半年ごとに要確認_
```

### 2.6 チャットログ（Slack / Teams / Chatwork）— 断片的な情報の蓄積

#### 前処理フロー

1. 「雑談・感情表現・スタンプのみ」の発言を除外
2. スレッドの文脈を保持して単一チャンクに結合
3. 「それ、どこに書いてある？」「マニュアル更新が必要だ」という発言を抽出し、ドキュメント更新フラグを立てる
4. 非公式決定（「じゃあそれで」「了解」）を正式決定フォーマットに変換

#### Before → After 実例

**Before（Slackログ）**

```
田中: 来週の月曜って全社会議あったっけ？
鈴木: あーあります！10時から第一会議室ですよ
田中: ありがとう
鈴木: あと確認ですが駐車場は社員用の第2駐車場が使えます
     （来客用は使わないでください）
```

**After（構造化 Markdown）**

```markdown
## Q: 社員が使える駐車場はどこですか？

**A:** 社員は「第2駐車場」を使用してください。
来客用駐車場は社員の使用不可です。

_情報源: 社内Slackチャンネル #総務連絡（2024-11-20）_
_⚠️ 公式文書での確認が推奨。最新状況は総務部へ問合せ_
```

### 2.7 文書タイプ別 変換手法サマリー

| 文書タイプ | チャンク単位 | 推奨サイズ | 最重要メタデータ | 注意点 |
|-----------|-----------|---------|--------------|-------|
| 業務マニュアル | 見出し単位 | 500〜800トークン | version, effective_date | 旧版を必ず除外 |
| FAQ集 | 1Q&Aペア | 制限なし | category, department | 類似質問バリエーション必須 |
| 社内規程 | 条文単位 | 300〜600トークン | effective_date, law_ref | 但し書きは本条と一体化 |
| 議事録 | 決定事項単位 | 200〜400トークン | meeting_date, decision_owner | 雑談・感情表現は除外 |
| 暗黙知 | 状況-判断-理由の1セット | 300〜500トークン | source_person, captured_date | 半年ごとに内容を検証 |
| チャットログ | スレッド単位 | 200〜400トークン | channel, date | 非公式発言は公式表現に変換 |

## 第3章：Q&Aデータの品質を決める「黄金ルール」

> **この章で学べること：** Q&Aデータの品質を最大化するための設計原則。質問文・回答文の書き方から、メタデータ設計、メンテナンスルールまでを体系化する。

---

### 3.1 1つのQ&Aペアの理想的な粒度

#### 推奨スコープ

| 要素 | 推奨範囲 | NG例 |
|------|---------|-----|
| 質問文 | 1トピック = 1質問 | 「AとBについて教えてください」 |
| 回答文 | 200〜500文字 | スクロールしないと読めない長文 |
| カバー範囲 | 1つの行動・判断に答える | 複数の手順を1つにまとめる |

#### 粒度の判断フロー

```
回答が500文字を超える
  → サブトピックに分割する

回答が3行未満
  → 関連トピックと統合を検討

「場合によって異なる」が多い
  → 条件別に複数Q&Aに分割する
```

---

### 3.2 質問文の書き方ルール（ユーザーが実際に聞く言い回し）

#### ルール一覧

**① 実際に従業員が打ちそうな言葉で書く（社内用語OK）**

| 種別 | 例 |
|------|---|
| ❌ NG | 「有給休暇の申請プロセスについて説明してください」 |
| ✅ OK | 「有給の取り方を教えて」「休暇って何日前に申請が必要？」 |

**② 類似質問バリエーションを最低3つ登録する**

```
メイン質問:      「有給休暇の申請方法は？」
バリエーション1: 「年休を取るにはどうすればいい？」
バリエーション2: 「休暇の申請期限はいつまで？」
バリエーション3: 「有給申請 手順」
```

**③ 否定形・トラブル形も登録する**

```
「有給が承認されない場合はどうすれば？」
「申請したのに反映されていない」
```

**④ 略語・英語・社内コード名も登録する**

```
「kintoneの休暇申請の方法」
「kintone 有給」
```

---

### 3.3 回答文の書き方ルール

#### 必須要素チェックリスト

- [ ] 最初の1文で端的に答える（**結論先出し**）
- [ ] 条件・例外事項がある場合は明記（「〜の場合を除く」）
- [ ] 手順は番号付きリストで記述
- [ ] 根拠（規程名・条文番号）を明記
- [ ] 更新日・有効期限を記載
- [ ] 問い合わせ先（部署・内線番号）を記載
- [ ] 「AI回答は参考情報です。詳細は一次ソースを確認してください」の免責文

#### NGパターン

| NGパターン | 問題点 | 修正方法 |
|-----------|-------|---------|
| 「担当者に確認してください」のみ | 回答になっていない | 担当者名・内線番号・問い合わせ方法を明記 |
| 「場合によります」を説明なしで使う | 判断基準が不明 | 「〜の場合はA、〜の場合はB」と条件を明示 |
| 「以前も説明しましたが」などの文脈依存表現 | 単独では意味不明 | 文脈なしで読んでも理解できる表現に修正 |

---

### 3.4 類似質問のバリエーション生成（表記ゆれ対策）

#### 対応すべき表記ゆれの種類

| 種類 | 例 |
|------|---|
| 漢字 vs ひらがな | 「有給」「ゆうきゅう」 |
| 正式名称 vs 略称 | 「年次有給休暇」「有給」「年休」 |
| 質問形式の違い | 「方法は？」「やり方」「手順」「取得するには」 |
| 英語・カタカナ混在 | 「kintone」「キントーン」 |
| 入力ミス・誤字 | 「有給」「有休」（どちらも使われる） |

### 3.7 「AIが答えるべきではない」判定基準

> ⚠️ 以下のカテゴリに該当する質問は、AIが回答してはいけません。必ず人間にエスカレーションしてください。

| カテゴリ | 具体例 | エスカレーション先 |
|---------|--------|----------------|
| 個人の人事評価 | 「私の評価はなぜ低いの？」 | 人事部・直属上長 |
| 法的判断・解釈 | 「これは違法ですか？」 | 法務部・顧問弁護士 |
| 機密・未公開情報 | 「新製品の発売日は？」 | 情報管理責任者 |
| 健康・医療相談 | 「この症状は何の病気？」 | 産業医・医療機関 |
| ハラスメント申告 | 「上司からXXされた」 | 人事部・ハラスメント相談窓口 |
| 個人情報照会 | 「Aさんの住所を教えて」 | 情報管理部門 |
| 懲戒・処分に関する内容 | 「就業規則違反の処分はどうなる？」 | 人事部・法務部 |

**実装方法：** システムプロンプトにエスカレーションキーワードリストを設定し、該当する質問には以下の固定回答を返す。

```
この件はAIでの回答が難しい内容です。
〇〇部（内線: XXX）または〇〇窓口にご相談ください。
対応時間: 平日 9:00-18:00
```

## 第5章：導入失敗事例と成功事例・ROI

> **この章で学べること：** 実際の失敗から学ぶ教訓と、定量データ付きの成功事例。ROI計算式で自社への導入効果を試算する。

---

### 5.1 失敗事例

#### ❌ 失敗事例1：「とりあえず全文書をベクトル化した」結果

**何が起きたか**

10年分のWordファイル（約3,000件）をそのままベクトルDBに投入。AIが廃止済みの残業申請フローを自信満々に案内し続けた結果、申請漏れによる給与未払いトラブルが発生。

**根本原因**

- バージョン管理なし
- 廃止ドキュメントの除外なし
- 有効期限メタデータ未設定

**教訓**

> 「精度の8割はデータの純度で決まる」。技術より前にデータ整理が必須。まず廃止ドキュメントを物理削除することが第一歩。

---

#### ❌ 失敗事例2：データ整備の工数を甘く見て途中で挫折

**何が起きたか**

「1ヶ月でナレッジベース構築完了」を目標に設定。実際には文書の整理・分類だけで3ヶ月かかり、予算が尽きてプロジェクト中断。

**根本原因**

- 文書整理の工数を実際の1/5に見積もっていた
- スコープを全社一斉展開で設定してしまった

**教訓**

> 「まず上位20%の質問（問い合わせ件数ベース）に絞る」スモールスタートが必須。全文書の整備は最終目標であって、スタート地点ではない。

---

#### ❌ 失敗事例3：AIが古い情報を自信満々に回答して業務事故

**何が起きたか**

システムUIが変更されたが、古いスクリーンショット付きマニュアルが残存。AIが旧手順を案内し続けた結果、正しく設定できない社員が続出。その後、設定ミスによる業務データの不整合が発覚。

**根本原因**

- 有効期限・更新日メタデータ未設定
- 定期見直しルールなし
- 複数バージョンが共存していた

**教訓**

> 有効期限切れチャンクの自動アーカイブ機能を必ず設定する。「情報の鮮度管理」はRAG運用の最重要タスク。

---

#### ❌ 失敗事例4：機密情報がAIの回答を通じて漏洩しそうになったケース

**何が起きたか**

人事評価シートや役員報酬データを含むExcelファイルを、アクセス制御設定なしでベクトルDBに取り込んだ。一般社員が特定の質問をするだけで、役員の報酬に近い情報を引き出せる状態になっていたことが社内テスト中に発覚。

**根本原因**

- アクセス制御（ACL）の設計がなかった
- 機密レベルの分類をせずに全ファイルを投入した
- ベクトルDBへの取り込み時に権限メタデータが剥がされた

**法的リスク**

- 個人情報保護法 第17条・第20条違反の可能性
- 不正競争防止法上の営業秘密管理義務違反

**教訓**

> 文書の機密レベル（public / internal / confidential / secret）を事前に分類し、レベル別のアクセス制御を設計してから取り込みを行う。「セキュリティは後付けでは対応できない」。

### 5.3 ROI計算フレームワーク

#### 計算式1：情報探索コストの削減

```
年間削減効果 =
  (現在の情報探索時間 - RAG導入後の探索時間)
  × 従業員数 × 平均時給 × 年間稼働日数
```

**試算例（中小企業50名・平均時給2,500円）**

| 項目 | 数値 |
|------|------|
| 現在の情報探索時間 | 15分/人/日 |
| 導入後の探索時間 | 5分/人/日 |
| 削減時間 | 10分/人/日 |
| **年間削減効果** | **10÷60 × 50名 × 2,500円 × 240日 ≒ 約500万円** |

---

#### 計算式2：新人の独り立ち期間短縮効果

```
新人教育コスト削減 =
  (現在の独り立ち期間 - 短縮後の期間)
  × 新人月次人件費 × 年間採用数
```

**試算例（月次給与25万円・年間採用3名・独り立ち期間 6→4ヶ月短縮）**

```
2ヶ月 × 25万円 × 3名 = 150万円/年
```

---

#### 計算式3：ベテラン社員の質問対応コスト削減

```
対応コスト削減 =
  ベテラン社員数 × 1日あたり質問対応時間
  × 時給 × 年間稼働日数 × 削減率
```

**試算例（ベテラン5名・1日2時間対応・時給3,500円・削減率70%）**

```
5名 × 2h × 3,500円 × 240日 × 0.7 ≒ 588万円/年
```

---

#### 試算サマリー（中小企業50名の場合）

| 効果項目 | 年間削減効果 |
|---------|------------|
| 情報探索コスト削減 | 約500万円 |
| 新人教育期間短縮 | 約150万円 |
| ベテラン質問対応削減 | 約588万円 |
| **合計（概算）** | **約1,238万円/年** |

> ※ 大規模試算例：社員1,000名の企業で1日10分の探索時間短縮（時給5,000円換算）では、年間 **約2億円規模** のリソースシフトが可能（KUSANAGI公式ブログ試算）。

### 5.4 セキュリティ・法的リスク管理

#### 個人情報保護法・不正競争防止法への対応

| リスク | 対策 |
|--------|------|
| 個人情報の無断取り込み | 取り込み前に個人情報の有無を確認・除外 |
| 機密情報のクラウドAIへの送信 | オンプレミス環境またはクローズドAI環境を採用 |
| アクセス制御の欠如 | 文書の機密レベル分類 + ロールベースアクセス制御 |
| 古い情報による誤回答 | 有効期限設定 + 定期的な再検証ルール |
| 著作権のある外部コンテンツの取り込み | 自社保有データのみを使用するルールを制定 |

#### 実装すべきセキュリティ設計

```
【4段階の機密レベル分類】
Level 1: public       → 全員がアクセス可能
Level 2: internal     → 全社員のみアクセス可能
Level 3: confidential → 特定部署のみアクセス可能
Level 4: secret       → 特定の役職者のみアクセス可能
          ※ RAGには原則取り込まない
```

## 🚀 まず今週できること 3ステップ

> **所要時間の目安：合計3.5〜4時間**

### Step 1：棚卸し（30分）

1. 問い合わせ担当者（総務・人事など）に「よく聞かれる質問TOP20」をヒアリング
2. それらの質問に対応する文書がどこにあるかをリストアップ
3. 文書の「最終更新日」と「現在も有効か」を確認

### Step 2：廃止ドキュメントの除外（1時間）

1. 共有フォルダ・ファイルサーバーを棚卸しし、3年以上更新されていない文書をリストアップ
2. 「廃止済み」「旧バージョン」のファイルを別フォルダに隔離（完全削除の前に確認）
3. 現行の正式文書を1箇所に集約

### Step 3：Q&A 5件を作成してテスト（2時間）

1. TOP20の中から最もよく聞かれる5件を選ぶ
2. この設計書の Markdown テンプレート（第4章）を使ってQ&A形式に変換
3. Dify（無料プランあり）またはNotebookLM（Googleアカウントで即利用可能）に投入してテスト
4. 実際に質問してみて回答を確認 → 改善点をメモ
